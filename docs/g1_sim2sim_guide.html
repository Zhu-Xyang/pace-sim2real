全局sim-to-sim 在验证什么

真机辨识只能看轨迹对不对得上，永远不知道辨识出的参数是不是真值。sim-to-sim 把“真机”换成一台参数由我们自己设定的仿真 G1，于是答案在手里：流程有 bug、参数不可辨识、优化器卡住，都会直接暴露成“恢复出的参数和真值对不上”。这一关过了，再上真机时出现的偏差才能归因到真机本身。

然后二选一装依赖。方案 A 最省事；方案 B 不往 sonic 里写任何东西，适合这个环境还被别的项目共用的情况。

方案 A：直接安装到 sonic

方案 B 的 export 只对当前终端有效，之后每开一个新终端都要重新执行。

python -c "import cmaes; print('cmaes', cmaes.__version__)"
python scripts/pace/fit_g1.py --help | head -3

判断标准

  • 第一行打印 cmaes 0.x，不报 ModuleNotFoundError。

步骤 3

设置环境变量

1 分钟

两个变量每个终端都要设。第二个尤其重要：Isaac Sim 退出时会直接结束进程，输出重定向到文件时缓冲区里的打印会全部丢失。

export OMNI_KIT_ACCEPT_EULA=YES     # 首次启动时不再交互确认许可
export PYTHONUNBUFFERED=1           # 等价于每次都加 python -u
ls -l $HOME/Code_prj/whole_body_tracking/source/whole_body_tracking/whole_body_tracking/assets/unitree_description/urdf/g1/main.urdf

判断标准

  • ls 能列出 main.urdf，大小约 40 KB。这是 29 自由度 rev 1.0 模型，质量惯量参数和 Unitree 官方文件一致。
  • 如果你的 URDF 放在别处，设置 export G1_URDF_PATH=/你的/路径/g1.urdf，辨识和以后的训练必须用同一份。

步骤 6

检查数据有没有“卡死”的关节

1 分钟

G1 的 PD 增益很低，如果某个关节的静摩擦大到指令推不动它，这个关节的惯量和阻尼就辨识不出来。下面这段脚本不需要 Isaac Sim，直接比较每个被激励关节的指令峰峰值和实际响应峰峰值。

python - <<'EOF'
import torch
d = torch.load("data/g1_29dof/g1_sim_legs_seed0.pt", weights_only=False)
t, q, qh, names = d["time"], d["dof_pos"], d["des_dof_pos"], d["joint_names"]
print("rows", q.shape[0], "cols", q.shape[1], "dt", round(float(t[1] - t[0]), 6),
      "excited", len(d["excited"]), "truth delay", d["truth"]["delay_steps"])
for j in d["excited"]:
    i = names.index(j)
    cmd = float(qh[:, i].max() - qh[:, i].min()); resp = float(q[:, i].max() - q[:, i].min())
    print(f"{j:26s} cmd {cmd:.3f}  resp {resp:.3f}  ratio {resp / cmd:.2f}")
EOF

判断标准

  • 29 列、步长 0.002、12 个被激励关节。
  • 每个关节的 ratio 都大于 0.3。本机实测在 0.59 到 1.21 之间：髋 pitch 大于 1 是共振放大，属于正常现象；踝 roll 最小，因为幅值只有 0.12 rad。

如果某个关节 ratio 小于 0.3　说明它被摩擦卡住了。换一个 --truth_seed 重新生成，或者把 --amp_scale 调大到 1.2 左右。

步骤 7

一致性检查：把真值原样交给拟合

2 分钟

这是最重要的一步。--floor_test 把所有参数的搜索范围收窄到真值本身，只跑一代。如果采集和拟合在时间对齐、零偏、延迟、初始状态上完全一致，4096 个环境算出来的损失应该接近浮点精度的零。

python -u scripts/pace/fit_g1.py --task Isaac-Pace-G1-Legs-v0 --headless --num_envs 4096 \
    --data g1_29dof/g1_sim_legs_seed0.pt --floor_test \
    2>&1 | grep -E "floor test|data columns|initialized|^\[it |Error|Traceback"

预期输出

[INFO] floor test: bounds collapsed onto the ground truth, 1 generation
[INFO] data columns 29, fitted 12, held 17; T = 11000 steps @ 0.002 s
CMA-ES (lite) initialized: 49 search dims, population 4095, probe=True
[it 0] min 1.6126e-14  max 2.9871e-13  mean-probe 2.8400e-13

判断标准

  • max 小于 1e-10 rad²。本机实测为 3e-13，比后面 A 档门槛 1e-8 小 4 个数量级。
  • fitted 12, held 17：12 个腿关节参与拟合，17 个腰和手臂关节按录制数据回放。

如果这里的损失明显大于 1e-10　先不要往下跑。说明采集和拟合对不上，常见原因是两边用了不同的 URDF 或增益，或者手动改过 SIM_DT。

这次一致性检查会在 logs/pace/g1_29dof_legs/ 下留一个运行目录。评估脚本默认读最新的目录，下一步正式拟合开始后，它自然成为最新的，不影响评估。

步骤 8

正式拟合

约 90 分钟

开一个专门跑拟合的终端。日志同时写到文件，方便在另一个终端里看进度。--max_iterations 100 是上限；参考运行在第 60 代就达到 A 档，到时可以提前停。

mkdir -p logs/pace
python -u scripts/pace/fit_g1.py --task Isaac-Pace-G1-Legs-v0 --headless --num_envs 4096 \
    --data g1_29dof/g1_sim_legs_seed0.pt --max_iterations 100 --save_interval 10 \
    2>&1 | tee logs/pace/fit_legs_seed0.log

在第二个终端里看进度。第一条命令看最近几代，第二条打开 TensorBoard，重点看 0_Episode/mean_probe_score 和直方图 0_Delay/distribution。直方图是样本延迟的分布，中心就是均值；0_Delay/best 只是最好样本的延迟，波动很大。

grep -E "^\[it " logs/pace/fit_legs_seed0.log | tail -5
tensorboard --logdir logs/pace/g1_29dof_legs

每一代打印的格式

[it 10] min 3.8485e-04  max 2.9793e-03  mean-probe 1.2817e-04
  Armature: [...]    ← 这 5 行都是本代最好的那个样本
  Viscous: [...]
  Coulomb: [...]
  Bias: [...]
  Delay: 2.3896...   ← 最好样本的延迟，不是均值，前 15 代会跳动
  elapsed 91.2 s

min 和 max 是 4095 个样本中最好和最差的分数。mean-probe 是本代开始时分布均值的分数，也就是上一代更新后的均值；mean_XXX.pt 存的是本代更新后的均值，两者只差一步更新，收敛后差别可以忽略。判定用的就是这个分数。

代数均值探针损失 rad²延迟均值（步）这时应该看到什么
03.2e-34.14起点：armature 1.22 倍先验，延迟 5 步
101.3e-43.01延迟取整已等于真值 3

判断标准

  • 每代约 90 秒，mean-probe 大体单调下降，可以有小幅回弹。
  • 判断延迟要看均值：用步骤 9 的评估脚本看 fitted mean 这一行（每 10 代一个检查点）。参考运行在第 10 代已是 3.01，之后一直在 3.x。每代打印的 Delay 是最好样本的值，第 9–14 代曾打出 1.55、2.39、4.59、2.68，不能单独拿来判断。
  • 若延迟均值长期停在 1.x 或 2.x、同时损失停在 1e-5 附近，就是掉进了延迟陷阱，见常见问题。
  • 达到 A 档后按 Ctrl+C 停止即可。检查点每 10 代写一次，最近的 mean_060.pt 已经在磁盘上。

判定规则

检查项A 档（损失 ≤ 1e-8）B 档（损失 ≤ 1e-7）
损失门槛均值探针损失必须小于 1e-7，否则直接 FAIL，不评参数
延迟拟合均值取整必须等于真值
armature≤ 10%，踝 roll ≤ 15%≤ 20%，髋 roll、膝 ≤ 25%，踝 roll ≤ 35%
阻尼、摩擦≤ 5%≤ 10%
自由零偏≤ 1.5 mrad，髋 roll ≤ 1.0，膝 ≤ 3.0≤ 2.0 mrad，膝 ≤ 8.0
髋 pitch + 膝零偏之和≤ 1.0 mrad≤ 2.0 mrad
  • 标 (pinned) 的零偏是被固定为 0 的关节：髋 yaw、踝、腰 yaw、腕。骨盆固定时重力几乎不加载它们，损失对零偏不敏感，所以不参与统计。
  • 髋 pitch 和膝的零偏单独看可以互相补偿，二者之和才确定小腿的绝对角度，所以另外检查它们的和。
  • 出现 TRAP SIGNATURE表示所有 armature 误差都为正、延迟取整又小于真值，就是掉进了延迟陷阱。

判断标准

  • 最后一行是 VERDICT: PASS (tier A, ...)，G1 腿部的 sim-to-sim 验证即告完成。

延迟扫描：固定延迟为 2、3、4 步

延迟是整数，损失对它是阶梯状的。把延迟分别钉在 2、3、4 步各拟合一次，比较最终损失：真值 3 步那次应当明显最低。这个方法在真机上也能用来确认延迟。

for K in 2 3 4; do
  python -u scripts/pace/fit_g1.py --task Isaac-Pace-G1-Legs-v0 --headless --num_envs 4096 \
      --data g1_29dof/g1_sim_legs_seed0.pt --fix_delay $K --max_iterations 60 --save_interval 10 \
      2>&1 | tee logs/pace/fit_legs_delay$K.log
done
结构对照：用原来的力矩延迟去拟合

数据是用指令延迟执行器生成的。改用原仓库的力矩延迟执行器拟合，损失应该停在明显高于本底的平台上。这说明两种结构在数据上可以区分，也说明为什么选择执行器结构要看留出数据上的损失。力矩延迟在 G1 上超过 2 步会失稳，所以这时延迟范围被限制为 0–2 步，真值 3 步本身就不在范围内。

python -u scripts/pace/fit_g1.py --task Isaac-Pace-G1-Legs-v0 --headless --num_envs 4096 \
    --data g1_29dof/g1_sim_legs_seed0.pt --torque_delay --max_iterations 60 --save_interval 10

执行器

延迟作用在哪里

utils/pace_actuator.py:60-66 → utils/pace_actuator_cmd_delay.py:70-78
原逻辑先算 PD 和裁剪，再把得到的力矩送进延迟缓冲： 
tau = super().compute(cmd, q - b, qd)
tau.joint_efforts = torques_delay_buffer.compute(...)
新逻辑先把指令 q̂、q̂̇ 和前馈力矩各自延迟，再用当前状态算 PD 和裁剪： 
cmd.joint_positions  = pos_buf.compute(...)
cmd.joint_velocities = vel_buf.compute(...)
cmd.joint_efforts    = eff_buf.compute(...)
return super().compute(cmd, q - b, qd)

为什么　Unitree 的电机 SDK 文档说明 PD 在电机端用最新的编码器读数计算，上位机只下发目标和增益，延迟主要在指令链路上，所以指令延迟更贴近硬件。这一点在 G1 上还没有实测，上真机前应先用阶跃响应确认。另一个原因是稳定性：用 G1 的低增益时，回路内的力矩延迟在 2 ms 步长下超过 2–3 步，踝和腕就会发散，CMA-ES 的大部分样本会变成 NaN。原类完全没动，ANYmal 仍然用它；G1 想对照时，拟合脚本加 --torque_delay 即可。

缓冲区与接口

pace_actuator.py:44-45 → pace_actuator_cmd_delay.py:48-68
原逻辑一个力矩缓冲，长度 max_delay + 1。
新逻辑位置、速度、前馈力矩三个缓冲，长度都是 max_delay。Isaac Lab 的 DelayBuffer 允许延迟取 0 到长度本身，所以 0–10 步都有效。update_encoder_bias、update_time_lags、reset 的签名和原类相同。

为什么　保持同样的接口，优化器和参数写入代码不用区分两种执行器。

优化器

env 0 用来评估当前均值

optim/cma_es.py:44, 106-109 → optim/cma_es_lite.py:169-173, 259-264
原逻辑4096 个环境全是 CMA 样本。报告的是更新后的均值，但这组均值本身从未被仿真过。
新逻辑env 0 每代跑当前的分布均值，其余 4095 个是样本。只有样本的分数交给 CMA-ES，均值的分数单独记为 mean-probe。

为什么　最终报告的参数就是均值，每代都能直接看到它的真实损失，评估脚本的损失门槛也基于这个数。严格说探针跑的是本代开始时的均值，mean_XXX.pt 是更新后的均值，二者差一步更新。代价是种群少一个样本。

armature 在对数空间搜索

cma_es.py:151-154 → cma_es_lite.py:185-192, 247-254；g1_pace_env_cfg.py 中 log_armature=True
原逻辑所有参数线性映射：lo + u·(hi − lo)。G1 的 armature 范围是 0.3–5 倍先验，起点在 2.65 倍。
新逻辑armature 用 lo·(hi/lo)^u，起点在几何中心 1.22 倍先验，每个数量级的分辨率相同。其余参数仍是线性映射。

为什么　这是在 G1 sim-to-sim 中实际踩到的坑：线性映射起点太重，拟合用偏短的延迟去补偿多出来的相位滞后，停在“延迟 1 步、armature 全部偏大 20–320%”的局部最优里（图 2 橙线）。换成对数映射后，第 10 代就找到了正确的延迟。

只拟合部分关节时的参数写入

cma_es.py:111-134 → cma_es_lite.py:86-139（write_pace_params_to_sim）
原逻辑用 argmax 把拟合关节对应到各执行器组。有两个问题：不在拟合列表里的关节，argmax 在全零列上返回 0，会被静默赋上第一个拟合关节的零偏；执行器组覆盖全部关节而只拟合子集时，索引会错位。
新逻辑先建一个覆盖全部关节的零偏张量，只在拟合关节上填值，再按各组的 joint_indices 切出来。未拟合的关节零偏为 0，并支持“按录制数据回放”的保持关节。采集脚本写真值时也用这同一个函数。

为什么　G1 有 5 个执行器组，而且按腿部、上身分开拟合，原映射会把错误的零偏写进被保持的关节。ANYmal 只有 1 个组且 12 个关节全部拟合，原代码在那里是对的，也继续在用。

其他小改动

cma_es_lite.py
  • 随机种子：原来写死 seed=0，现在是参数，拟合脚本用 --seed 传入。
  • 参数共享：可选让左右对称关节或同型号电机共享 armature、阻尼、摩擦，零偏始终逐关节、延迟始终全局。默认不共享，与原布局相同。
  • NaN 保护：发散样本的分数被换成一个大的有限值，避免破坏 CMA-ES 的排序。原来没有。
  • 停止条件：(max − min)/min 加了除零保护，其余不变。

数据采集脚本

真值怎么来

scripts/pace/data_collection.py:60-64 → scripts/pace/data_collection_g1.py:131-167
原逻辑所有关节用同一组写死的值：armature 0.1、阻尼 4.5、摩擦 0.05、零偏 0.05、延迟 5 步。其中延迟 5 步正好是搜索范围 0–10 的中心，也就是 CMA-ES 的起点。
新逻辑按 --truth_seed 为每个关节单独抽取：armature 0.5–3 倍先验、阻尼取范围的 10–90%、摩擦 0.3–1.2 倍先验、零偏 ±0.03 rad，重力看不见的关节零偏为 0，延迟默认 3 步。超出拟合范围会报错。

为什么　各关节取值相同，就测不出关节对应错位的问题。真值落在起点上，就测不出搜索能力。真值要分布在起点两侧：第一次跑时真值全在一侧，正是它把拟合推进了延迟陷阱。摩擦不超过 1.2 倍先验，是为了不让关节被静摩擦卡住。

激励轨迹

data_collection.py:92-117 → data_collection_g1.py:76-122
原逻辑所有关节共用一条 0.1–10 Hz 的 chirp，用 ANYmal 专用的方向、偏置、幅值三个 12 维向量变换，所有关节同时运动，没有静止段和淡入淡出。
新逻辑
  • 以站立中心姿态为基准：静止 1 秒 → chirp 20 秒 → 静止 1 秒，淡入淡出 2 秒。
  • 每类关节有自己的幅值和频率上限。
  • 只激励 --group 选中的那一组关节。
  • 左右不镜像。
  • 支持用 --plan 回放外部指令文件。

为什么　G1 的关节多、增益低、共振频率各不相同，统一的大幅值会让一部分关节饱和，另一部分几乎不动。只激励一组关节，才能让分组拟合保持严格正确。髋部左右镜像会让两脚距离缩到 0.12 m，在真机上可能相撞。

任务Isaac-Pace-Anymal-D-v0Isaac-Pace-G1-v0、-Legs-v0、-Upper-v0

为什么　腰部加大增益，是因为骨盆固定后上身像倒立摆，重力刚度约 −21 N·m/rad（代码取 −20.62），按行走增益会下垂到 ±0.52 rad 的限位上。零偏只能通过重力体现，重力不加载的关节放开零偏，它就会随机游走，最后被当成编码器偏置带进训练。只拟合一组关节，靠的是骨盆固定后两腿和“腰加双臂”是根节点下互不影响的分支。

注册、导出与评估

原逻辑tasks/manager_based/__init__.py 只注册 ANYmal；optim 只导出 CMAESOptimizer；utils 只导出 PaceDCMotor(Cfg)。没有和真值对比的工具，plot_trajectory.py 只画曲线。
新逻辑在 tasks/manager_based/__init__.py 末尾追加 3 个 G1 任务注册；新执行器的导入加在 utils/__init__.py 原有导入之后，optim/__init__.py 的 __all__ 扩写为包含原名字的列表；顶层 pace_sim2real/__init__.py 未动；新增 eval_g1_sim2sim.py，按损失门槛和分档阈值给出判定。

为什么　不删除、不改名任何已有的导出，原有的 import 路径全部有效。

之后上真机前要记住的几点

  • 同一套约定：真机录制也要是 2 ms 一行、SDK 顺序 29 列、带 joint_names、excited、kp、kd，这样 fit_g1.py 不用改就能吃真机数据。
  • 第 k 行的读数必须在第 k 行指令生效之前采样，而且录制开始时机器人要静止。错一行就是 2 ms，会被延迟参数吸收掉。
  • 骨盆必须刚性夹住，不能用绳子吊：吊绳约 0.4–0.7 Hz 的摆动落在扫频范围里。
  • armature 在现有增益下辨识得最慢：用 BeyondMimic 增益时，踝关节的阻尼项约为惯量项的 5 倍，可考虑为辨识单独降低 kd。
  • 训练时的步长和执行器类要和辨识时一致：步长 0.002 s，执行器 PaceDCMotorCmdDelay，max_delay 填辨识出的延迟向下取整。
